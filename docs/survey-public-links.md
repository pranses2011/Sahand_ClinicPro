# پیوند پیامکی نظرسنجی

سرویس داخلی پاسخ‌گویی عمومی جدید در مسیر `/s/` به‌طور پیش‌فرض خاموش است و پیش از بهره‌برداری به پیکربندی و آزمون استقرار نیاز دارد؛ جزئیات آن در بخش پایانی آمده است. API داخلی و فرم دسکتاپ با احراز هویت نیز می‌توانند پاسخ جداگانهٔ سؤال‌ها را به صورت ناشناس ثبت کنند. سازندهٔ سؤال یا صف پیامک به‌تنهایی به معنی آماده بودن نظرسنجی آنلاین نیست.

برای اتصال به یک سرویس پاسخ‌گویی مستقل که این مسیر را پیاده کرده، پس از بررسی دسترس‌پذیری، امنیت و حریم خصوصی آن، نشانی پایهٔ HTTPS را در تنظیمات API با کلید `Surveys:PublicBaseUrl` تعیین کنید (متغیر محیطی معادل: `Surveys__PublicBaseUrl`). API برای هر شناسه مسیر `/s/{id}` را به انتهای نشانی اضافه می‌کند. کلاینت‌های مستقیم API همچنین می‌توانند `baseUrl` معتبر را در درخواست بفرستند. از نسخهٔ جدید، بدون نشانی صریح یا با نشانی نامعتبر هیچ پیامکی به صف اضافه نمی‌شود. این کنترل صرفاً شکل نشانی را اعتبارسنجی می‌کند و صحت، امنیت یا کارکرد سرویس خارجی را تضمین نمی‌کند.

ارسال فقط صف‌گذاری پیامک برای ویزیت‌های شروع‌شده، در جریان یا تکمیل‌شدهٔ همان روز به وقت ایران و دارای شماره غیرخالی است و به معنی تحویل قطعی نیست. ارسال مجدد از ایجاد پیامک تکراری جلوگیری نمی‌کند؛ اپراتور پیش از تأیید باید ارسال‌های قبلی را بررسی کند. راه‌اندازی سرویس عمومی، حفاظت در برابر ثبت پاسخ تکراری و سوءاستفاده، و آزمون سرتاسری پیامک همچنان نیازمند پیاده‌سازی و بررسی جداگانه است.

## ثبت داخلی و محرمانگی

فرم داخلی پاسخ را بدون شناسهٔ بیمار، ویزیت یا پزشک ارسال می‌کند. از این
تغییر، متن بدنهٔ درخواست ثبت پاسخ در لاگ عملیات کپی نمی‌شود؛ خود عملیات و
کاربر ثبت‌کننده همچنان قابل ثبت‌اند، و پاسخ‌ها و نظرات در جدول نتایج ذخیره
می‌شوند. لاگ‌های تاریخی خودکار پاک نمی‌شوند. این تدابیر به‌تنهایی تضمین
ناشناس‌ماندن یا رعایت همهٔ الزامات حریم خصوصی نیستند؛ محدودکردن دسترسی به
نتایج و لاگ‌ها و سیاست نگهداری اطلاعات همچنان لازم است.

## سرویس داخلی اختیاری (در دست توسعه و نیازمند آزمون استقرار)

سرویس داخلی با `Surveys:EnableBuiltInPublic=true` و تنظیم
`Surveys:PublicBaseUrl` به نشانی عمومی HTTPS فعال می‌شود. مقدار پیش‌فرض
خاموش است؛ در حالت داخلی، نشانی `baseUrl` در درخواست اپراتور نادیده گرفته
می‌شود تا توکن به دامنهٔ دلخواه درخواست‌کننده ارسال نشود. برای هر پیامک یک
توکن تصادفی ۲۵۶ بیتی ساخته می‌شود و تنها چکیدهٔ آن در جدول دعوت نگهداری
می‌شود؛ دعوت پس از هفت روز منقضی است. token در fragment لینک قرار دارد تا
در URL درخواست معمولی وب، query string و لاگ مسیر سرور دیده نشود؛ صفحه پس
از بازشدن آن را در بدنهٔ درخواست HTTPS ارسال می‌کند. فرستادن پاسخ و مصرف
دعوت در یک SaveChanges تراکنشی با کنترل تعارض انجام می‌شود. پاسخ داخلی
شناسهٔ بیمار، ویزیت و پزشک را همراه خود ذخیره نمی‌کند. سؤال‌ها در زمان
ثبت کنترل و متن آن‌ها در پاسخ ذخیره می‌شود.

**استقرار ایمن شرط استفاده است:** دامنه باید به یک reverse proxy عمومی با
TLS معتبر و فقط مسیرهای `/s`، `/s/`، `/s/read` و `/s/submit` هدایت شود؛
API داخلی، Swagger، فایل‌ها و سایر مسیرها نباید برای عموم باز شوند. نرخ
درخواست در برنامه برای هر IP و هر نمونه محدود است؛ در proxy نیز محدودیت
مستقل و حفاظت در برابر حمله لازم است. برنامه هدرهای IP ارائه‌شده توسط
کاربر را برای این محدودیت نمی‌پذیرد، پس ممکن است همهٔ کاربران پشت یک proxy
یک سهمیه داشته باشند. لاگ بدنهٔ درخواست، گزارش خطا، ابزارهای ردیابی و
لاگ‌های پروکسی برای این مسیرها باید خاموش شوند؛ توکن و متن پاسخ را ثبت
نکنند. وابستگی به TLS، عایق‌سازی شبکه، حفاظت از دیتابیس و پشتیبان، و
بررسی تنظیمات واقعی proxy ضروری است.

متن پیامک و توکن تا زمان پاک‌سازی صف پیامک و احتمالاً در سامانهٔ ارائه‌دهندهٔ
پیامک یا تلفن گیرنده موجود است. دسترسی به صف و پشتیبان‌ها را محدود و سیاست
حذف و نگهداری تعریف کنید؛ زمان ثبت پاسخ، نظر آزاد، یا لاگ‌های دیگر ممکن است
باعث شناسایی شوند. بنابراین ناشناس‌بودن مطلق تضمین نمی‌شود. هیچ گزینه‌ای
در فرم بیمار برای ثبت اطلاعات هویتی ندارد، با این حال بیمار ممکن است در
متن آزاد اطلاعات حساس بنویسد. ارسال مجدد هنوز توکن‌های مجزا و پیامک
تکراری می‌سازد، و این سامانه حفاظت توزیع‌شده در چند نمونه یا تضمین تحویل
پیامک ندارد. پیش از استفاده باید migration روی SQL Server، رقابت ثبت موازی،
صف واقعی پیامک، مرورگر تلفن همراه، TLS و استقرار reverse proxy در محیط
هدف آزموده شوند. سرویس بیرونی قبلی در حالت خاموش همچنان مستقل است.

## سازگاری و ویرایش همزمان

فهرست نظرسنجی‌ها اثر انگشت نسخه را به کلاینت می‌دهد. ویرایش، تغییر وضعیت و
حذف نرم بدون نسخهٔ مشاهده‌شده یا با نسخهٔ قدیمی رد می‌شوند؛ خطای تداخل SQL
نیز به ۴۰۹ تبدیل می‌شود. سرور و هر دو صفحهٔ دسکتاپ باید همزمان ارتقا یابند؛
کلاینت قدیمی از این عملیات روی سرور جدید پشتیبانی نمی‌کند. بعد از خطا، پیش
از تکرار فهرست را تازه‌سازی و تغییرات ذخیره‌نشده را بازبینی کنید.

در ویرایش صرف عنوان یا توضیح، JSON سؤال‌های دست‌نخورده عیناً حفظ می‌شود؛
ساختار ناشناخته یا کلید تکراری در طراح بازنویسی نمی‌شود. حذف نرم پاسخ‌ها را
از دیتابیس پاک نمی‌کند ولی نظرسنجی و نتایج آن از رابط برنامه خارج می‌شود و
بازیابی از همان صفحه پشتیبانی نمی‌شود. آزمون CI و شبیه‌سازی تعارض جایگزین
آزمون همزمانی واقعی SQL Server یا استقرار عمومی نیست.
