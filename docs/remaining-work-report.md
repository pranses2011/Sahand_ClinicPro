# گزارش متمرکز اصلاحات باقی‌مانده

این گزارش وضعیت شناخته‌شده شاخهٔ کاری را ثبت می‌کند؛ وجود یک مورد در فهرست به معنی رفع یا آزمون موفق آن نیست. موارد آزمون‌نشده در محیط درمانگاه تا زمان تأیید عملی باز می‌مانند.

## ۱. طرح تأییدشده و طراح چاپ

- [ ] تطبیق پیکسل‌به‌پیکسل صفحهٔ پیاده‌شده با `docs/design/print-template-new-proposal.png` هنوز حاصل یا تأیید نشده است. ساختار و محتوای پنل‌ها و بوم همچنان تفاوت‌های قابل‌مشاهده دارند.
- [ ] مقایسه در حالت‌های مختلف اندازهٔ پنجره، مقیاس ویندوز، فونت، داده و اسکرول انجام شود. `docs/design/compare.html` مقایسهٔ تصویری فراهم می‌کند؛ تصویر هم‌اندازهٔ `docs/screenshots/real/print-designer-layout.png` رندر WPF خارج از صفحه با DPI مقیاس‌شده است و جایگزین تصویر واقعی مانیتور نیست. تصویر واقعی در `docs/screenshots/real/print-designer.png` قرار دارد.
- [ ] کشیدن واقعی ابزار و عنصر، هشت دستگیره، لغو حرکت با Escape یا قطع capture، ترتیب لایه، اسکرول و بزرگ‌نمایی در محیط تعاملی ویندوز آزموده شوند. آزمون خودکار WPF لغو رویداد ساختگی هر هشت دستگیره و بازگشت هندسه را نیز بررسی می‌کند، اما آزمون فیزیکی ماوس و capture واقعی نیست.
- [ ] خروجی دادهٔ واقعی، جدول‌های طولانی، حاشیه، صفحه‌بندی، اندازه و جهت کاغذ و چاپ فیزیکی روی چاپگرهای هدف آزموده شوند. نمایش جدول نمونه روی بوم تقریبی است و محافظ سرریز تضمین صفحه‌بندی یا رفتار درایور نیست.
- [ ] عملکرد همهٔ مسیرهای طراح، ذخیره و بازخوانی قالب‌های موجود، سازگاری داده‌های قدیمی و رفتار لغو تغییرات به‌صورت انتهابه‌انتها بازبینی شود.

## ۲. تنظیمات و جریان چاپ

- [ ] تنظیمات تمام‌عرض، تعداد نسخه‌ها، انتخاب چاپگر و پیش‌نمایش در همهٔ مسیرهای متصل با چاپگر واقعی و حالت انصراف آزموده شوند. در پیش‌نمایش HTML نتیجهٔ نهایی چاپ یا انصراف مرورگر قابل تأیید نیست؛ بسته‌شدن خودکار آن نباید موفقیت چاپ را جعل کند.
- [ ] قبض قدیمی پذیرش، قالب پیش‌فرض آن و خروجی واقعی سایر قالب‌ها با نمونه‌های مورد تأیید و دادهٔ واقعی بررسی شوند.
- [ ] پوشش و کارکرد واقعی میانبرهای قابل‌مشاهدهٔ تمام دکمه‌های ثبت و ذخیره، از جمله موارد تعارض، بررسی شود.

## ۳. فرم‌ها و جریان‌های بالینی و مالی

- [ ] همهٔ فرم‌های بازطراحی‌شده با طرح تأییدشده و عملکرد واقعی خود مقایسه شوند؛ صرف نمایش کنترل‌ها کافی نیست. به‌ویژه تطبیق و عملکرد صفحات دندان‌پزشکی، فیزیوتراپی، چشم‌پزشکی، نظرسنجی، پذیرش و تصویربرداری بازبینی شود؛ یادداشت دندان جای رزرو واقعی را نمی‌گیرد.
- [ ] پذیرش و نوبت جدید با دادهٔ واقعی، پاسخ‌های دیررس، خطا و ریست کامل انتهابه‌انتها آزموده شوند. زنجیرهٔ پذیرش تا پرداخت یک تراکنش اتمی واحد نیست.
- [ ] بازیابی و تکرار امن پرداخت، فاکتور و پذیرش با سناریوهای واقعی قطع ارتباط، چند کاربر، تغییر دستگاه یا حساب و بازیابی پایگاه بررسی شود؛ نگهداری محلی اطلاعات بازیابی هماهنگی بین دستگاه‌ها را تضمین نمی‌کند. نصب تمیز و ارتقا، بازپخش در کانتکست تازه و رقابت هم‌زمان یک کلید پرداخت روی SQL Server آزمایشی CI اجرا شده‌اند؛ این جایگزین آزمون شبکه، دستگاه و محیط درمانگاه نیست.
- [ ] حسابداری، حساب پیش‌فرض و نگاشت روش‌های پرداخت، گردکردن و موارد بیمه و مصرفی با قواعد مالی مورد تأیید و دادهٔ واقعی بررسی شوند. صدور یا پرداخت جدید در نبود حساب لازمِ فعال و قابل سند شدن اکنون رد می‌شود؛ بازپخش موفق قبلی همچنان ممکن است. نگاشت پیشین روش‌های پرداخت به صندوق `1101` عمداً تغییر نکرده و باید توسط مسئول مالی تأیید شود.
- [ ] مسیرهای نسخه، ویزیت، ارجاع، آزمایش، تصویربرداری و مصرف چند بچ در رقابت SQL و با دادهٔ واقعی بررسی شوند. صحت بالینی داده‌های تصویربرداری و DICOM سفارشی جداگانه نیازمند تأیید است.
- [ ] مسیر عمومی نظرسنجی، رقابت پایگاه داده و ارسال و ارسال مجدد پیامک با زیرساخت واقعی آزموده شوند؛ آزمون‌های SQLite جایگزین SQL Server و سرویس پیامک نیستند.

## ۴. نصب و بازیابی پایگاه داده

- [ ] خطای گزارش‌شدهٔ مجوز بازیابی و تنظیم نقش SQL روی محیط واقعی کاربر، با حساب اتصال واقعی API و حساب دارای مجوز مدیریتی، بررسی شود. موفقیت اسکریپت یا تست‌های ایستا به‌تنهایی موفقیت `RESTORE` را ثابت نمی‌کند.
- [ ] نصب کامل و ارتقا از نسخهٔ موجود، حفظ پیکربندی و بارگذاری وابستگی‌های جدید روی ویندوز و SQL Server محیط هدف آزموده شوند. migration نصب تمیز و ارتقا از نسخهٔ پیش از شناسه‌های درخواست در کانتینر آزمایشی SQL Server 2022 بررسی شده، نه روی نسخهٔ پشتیبان واقعی کاربر. روش پشتیبان‌گیری و بازگشت عملی نیز باید تأیید شود.

## ۵. ساخت، انتشار و مرج

- [ ] ساخت بدون خطا و بدون هشدار، از جمله هشدارهای سرکوب‌شده، جداگانه بررسی شود؛ موفقیت CI به‌تنهایی اثبات صفر هشدار مطلق نیست.
- [ ] پس از تکمیل و تأیید اصلاحات، بسته‌های نصب و به‌روزرسانی جدید مطابق درخواست کاربر ساخته و بررسی شوند؛ سپس مرج و پاک‌سازی شاخه‌های اضافی طبق دستور کاربر انجام شود. این گزارش به‌تنهایی به معنی انجام انتشار یا مرج نیست.

## وضعیت بررسی ثبت‌شده

- در CI قبلی، خروجی حلقهٔ آزمون‌های لینوکس از طریق `tee` در زیرپوسته اجرا می‌شد و وضعیت شکست به گام اصلی منتقل نمی‌شد؛ بنابراین سبز بودن بخش آزمون آن اجرا سند موفقیت همهٔ تست‌ها نیست. انتقال وضعیت اصلاح و آزمون‌های قدیمی مالی با قرارداد فعلی هماهنگ شدند؛ نتیجهٔ اجرای جدید باید جداگانه بررسی شود.
- در [اجرای SQL Server 41120157001](https://github.com/pranses2011/Sahand_ClinicPro/actions/runs/41120157001) برای کامیت `0b2fad9`، سه آزمون نصب تمیز migration، ارتقای آزمایشی همراه با بازپخش متوالی پذیرش/فاکتور/پرداخت و رقابت هم‌زمان یک کلید پرداخت موفق شدند. آزمون روی کانتینر SQL Server 2022 با پایگاه موقت و حساب آزمایشی بود، نه مجوز RESTORE یا پایگاه واقعی درمانگاه.
- آزمون‌های ویندوزی WPF و E2E لایسنس در [اجرای 41120157087](https://github.com/pranses2011/Sahand_ClinicPro/actions/runs/41120157087) برای همان کامیت موفق شدند؛ این به معنی ماوس تعاملی یا چاپ فیزیکی نیست. نتیجهٔ کل اجرای لینوکس را جداگانه ببینید.
- [رندر ویندوزی صفحات چاپ 41120410203](https://github.com/pranses2011/Sahand_ClinicPro/actions/runs/41120410203) در کامیت `6ee7b41` آرتیفکت غیرتعاملی ساخته است؛ بررسی ظاهری و تطبیق پیکسلی تأیید نشده و این رندر چاپ فیزیکی نیست.
- فرمان‌های تو‌در‌تو اکنون در تراکنش مشترک باقی می‌مانند؛ شکست داخلی تمام واحد کار را برگشت‌پذیر می‌کند. پیشنهاد لیست انتظار در صف پیامک ثبت می‌شود، نه ارسال مستقیم قبل از commit؛ صف‌شدن به معنی تحویل پیام نیست. تخصص انتخاب‌شده و شماره معتبر در انتخاب رعایت می‌شوند؛ محدودهٔ ساعت صبح/عصر/شب هنوز تعریف و اعمال نشده و نیاز به تأیید قواعد درمانگاه دارد.
- PR، بستهٔ نصب، انتشار و مرج جدیدی برای تغییرات این نوبت ایجاد نشده است. انتشار پیشین `v2.28.33` شامل اصلاحات پس از آن انتشار نیست.
- چاپ فیزیکی، RESTORE با مجوز کاربر، نصب و ارتقای واقعی، و تطبیق پیکسلی تأیید نشده‌اند.
